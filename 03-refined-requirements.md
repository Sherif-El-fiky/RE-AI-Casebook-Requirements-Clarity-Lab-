# Refined Requirements

Format: ID, requirement statement, rationale, verification method - consistent with standard CPRE/INCOSE-style requirement quality criteria (atomic, unambiguous, testable, traceable).

| ID | Requirement | Rationale | Verification |
|---|---|---|---|
| REQ-001 | The system shall authenticate a valid badge or fingerprint credential and unlock the associated entry point within 2 seconds under normal operating load. | Replaces "quickly" with a measurable target; 2s selected as a reasonable baseline for a single-lane entry pending confirmation with Facilities on acceptable throughput at peak hours. | Timed test, 50 consecutive authentication attempts, 95th percentile ≤ 2s |
| REQ-002 | Standard employee users shall be able to complete a successful entry without reference to a user manual or completing formal training, verified via a first-use usability test with 5 representative users. | Converts "user-friendly, no training" into an observable, testable criterion rather than a subjective claim. | Usability test with untrained participants; success criterion = 4/5 complete entry unaided |
| REQ-003 | Access to designated restricted areas (see REQ-003a area list - **open item, pending Facilities/IT Security confirmation**) shall be granted only to users whose HR role attribute matches the area's approved role list. | Formalizes role-based access as an explicit allow-list model per RE clarification with IT Security, rather than leaving it implicit. | Access control matrix review + penetration test of denied-role access attempts |
| REQ-004 | The system shall support a minimum of [TBD - pending confirmed target from Facilities headcount plan] concurrent registered users, with architecture allowing horizontal scaling without redesign. | "Large number... growing a lot" is not verifiable without a number; flagged as an open item requiring a follow-up with Facilities rather than an invented figure. | Load test at target concurrency; architecture review |
| REQ-005 | All access events (grant, deny, and forced/emergency unlock) shall be logged with timestamp, user ID, and location, retained for [TBD - pending compliance/legal input on retention period], and accessible only to authorized security administrators. | Converts "keep a log... in case something happens" into a complete, testable logging and access-control requirement. | Log review + access-permission audit |
| REQ-006 | Upon a report of a lost or stolen badge via the designated Facilities/IT channel, the associated credential shall be revoked from the access control system within 15 minutes during business hours. | Replaces "deal with it quickly" with a defined SLA and a defined reporting channel (both missing from the raw input). | Timed process test: report-to-revocation interval |
| REQ-007 | **[Safety-critical]** Upon receipt of a verified fire alarm signal, all controlled entry/exit points on the emergency egress path shall automatically unlock (fail-open), independent of the access control system's normal operating state, in compliance with applicable local fire and building safety code. | Elevated to its own safety-classified requirement rather than bundled under general "reliability" - this carries legal/code compliance weight, not just an SLA. | Fire-alarm-triggered fail-open test, performed jointly with fire safety compliance sign-off |
| REQ-008 | Visitor access is **out of scope for this requirement set** pending a dedicated visitor-management workshop with Facilities and Reception; to be captured as a separate requirement package. | Explicitly scoped out rather than guessed at, per stakeholder input that was itself undefined ("somehow"). | N/A - scoping decision, not a requirement |

**Open items requiring stakeholder follow-up before baseline:** REQ-003a (restricted area list), REQ-004 (target user count), REQ-005 (log retention period), REQ-008 (visitor access scope).
